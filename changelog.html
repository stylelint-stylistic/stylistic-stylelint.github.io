Changelog ​

All notable changes to this project will be documented in this file.

The format is based on Keep a Changelog, and this project adheres to Semantic Versioning.

Unreleased ​

Changed ​

  • The rules no longer read an SCSS stylesheet (postcss-scss) under their core names: such a file now gets one warning naming the @stylistic/scss/ namespace, which holds the same rules with the same options and documentation, and nothing else of it is checked. A project linting SCSS renames the rules in the overrides block that sets customSyntax — @stylistic/scss/color-hex-case in place of @stylistic/color-hex-case — and everything else stays as it was: plain CSS, and a plain block of an HTML page beside a lang="scss" one, the namespace reads exactly as the core does. With this the core is written for plain CSS alone, and its reading of a plain CSS file narrows where it used to pass a construct only Sass spells over as one: a reading through a Sass module (ns.$a, ns.f()), a placeholder selector (%a), a nested property (font: { … }), an at-rule carrying neither block nor parameters, and a comment the parser itself marked as opened by a double slash are read as the CSS they are. What a plugin spells over plain CSS the core still passes over as it did — a $ variable, its map or list, and the $(…) of postcss-simple-vars, an interpolation (#{…}, @{…}) and the text inside it — since a file linted with such a plugin is a plain CSS file to Stylelint, and a fix that read those as code would rewrite them.
  • The rules no longer read a Less stylesheet (postcss-less) under their core names: such a file now gets one warning naming the @stylistic/less/ namespace, which holds the same rules with the same options and documentation, and nothing else of it is checked. A project linting Less renames the rules in the overrides block that sets customSyntax — @stylistic/less/color-hex-case in place of @stylistic/color-hex-case — and everything else stays as it was: plain CSS, and a plain block of an HTML page beside a Less one, the namespace reads exactly as the core does. One reading of plain CSS narrows with the turning: a value opening with @, which the core used to pass over as a Less variable, is read as the CSS it is, so unit-case now reports a miscased unit in a value such as @{}10PX.
  • The rules no longer read a styled template (postcss-styled-syntax) under their core names: such a file now gets one warning naming the @stylistic/styled/ namespace, which holds the same rules with the same options and documentation, and nothing else of it is checked. A project linting styled templates renames the rules in the overrides block that sets customSyntax — @stylistic/styled/indentation in place of @stylistic/indentation — and everything else stays as it was, plain CSS included, which the namespace reads exactly as the core does.
  • The documentation now lives at stylelint-stylistic.github.io/stylelint-stylistic, and the URL a rule reports beside its problems (meta.url) points at that rule's page there instead of its README.md on GitHub. A rule carries the same URL under every namespace, since the rule and its documentation are the same; what a namespace reads differently is written on a page of its own, linked from the Custom syntaxes guide.
  • The named-grid-areas-alignment rule now reads the rows of the grid-template and grid shorthands as it reads the value of grid-template-areas (see #45): every string at the top level of the value is a row, its cells are aligned with the cells of the other rows, and a row's size, its line names, the solidus and the columns behind it go back as the file spells them. A stylesheet spelling its grids with a shorthand meets the rule's warnings on them now, where it used to pass them in silence, and --fix aligns their cells; under alignQuotes the sizes behind the rows come to stand in a column of their own. The message names the property the value belongs to.
  • The plugin now reads a line break the way PostCSS does: a line feed, with or without the carriage return of a Windows pair in front of it, and nothing else. A bare carriage return and a form feed are whitespace to every rule, as they are to PostCSS's line counter — a rule reading a line in either reported a position the file does not have, since Stylelint counts lines by PostCSS. Every rule about a break, an empty line, an inline comment's end or a multi-line list is affected: a file broken with bare carriage returns or form feeds is one line to all of them now. The linebreaks rule tells \n from \r\n and leaves a bare carriage return where it stands.
  • Every rule that writes a line break now writes the one the linebreaks rule asks for, wherever the configuration lists that rule, and otherwise the one the file spells its lines with (see #352). Stylelint runs each rule once and in the order the configuration lists them, so a break another rule wrote behind linebreaks used to stay a line feed in a file of Windows pairs until the next run of --fix; there is no order the two disagree in any more. A file that ends no line at all is given a line feed, never the line ending of the machine.
  • The declaration-block-trailing-semicolon rule now writes the semicolon its always option adds behind a declaration with whatever the declaration-block-semicolon-newline-before and declaration-block-semicolon-space-before rules ask to stand in front of one, wherever the configuration lists either of them (see #354), and the one it adds behind an at-rule with whatever the at-rule-semicolon-space-before rule asks for, which has no fixer to put it there itself (see #477). Stylelint runs each rule once and in the order the configuration lists them, so a bare semicolon written behind one of those rules used to stay bare until the next run of --fix — and behind an at-rule for good, since that rule has no fixer — and the block spelled its last semicolon unlike the others; there is no order the rules disagree in any more.
  • A rule configured with a -single-line or -multi-line option now takes its turn in the plugin's own order rather than in the one the configuration happens to list it in (see #502). The check of such a rule waits for the run's writers already (see #355), and behind that line two of them used to answer between themselves in the configuration's order: --fix left one file where a rule stood in front of its neighbour and another where it stood behind, and often one of the two files still violated a rule the user had turned on. Reordering two such entries changes nothing now — the order among them is the text whose lineness a rule reads, innermost first, a call's arguments before the declaration around them and the declaration before the statement's own prelude and block, with the rules whose subject is a line break in front of the rules whose subject is a space, and the options about a single-line text in front of the options about a multi-line one. Of the 105 and 95 rows measured over two corpora where the two orders left different files, 61 and 53 had one order leaving a rule unsatisfied; none does now. The same holds for one rule listed under two namespaces, @stylistic/indentation beside @stylistic/scss/indentation for one, which a plain CSS file is read by both of: those are ordered by the namespace, the core's first. A pair of which at least one rule carries no such option is untouched by all this, and can still answer differently under the two orders.
  • False negatives are fixed — a violation the plugin used to pass over in silence, whether --fix was asked for or not, is now reported:
    • The named-grid-areas-alignment rule now reads its properties in whatever case they are written (see #614). It matched grid-template-areas in lower case alone, so GRID-TEMPLATE-AREAS: "a a" was passed over — and with property-case: "upper" listed ahead of it, --fix uppercased the property first and the rule read nothing behind it, so the two orders of the configuration left two files and neither carried a warning.
    • The declaration-colon-space-after and declaration-colon-space-before rules now find the declaration's colon the way its parser found it (see #92). What the file spells between the property and the value is handed to the tokenizer that parser reads by, so a colon standing inside a comment, a string, a parenthesised group, an at-word or an escape is text there and opens no declaration. The search these rules used read a comment by rules of its own — it never closed one whose text ends in a backslash, /*x\*/, and it read the */ and /* of two comments abutting as opening a third — and it took a double slash for a comment in every file and wherever it stood, so a { b/*x\*/:pink; }, a { b/*x*//*y*/:pink; }, a { b //: red; }, a { b //"x:": red; } and a { b $//: red; } were passed over by every option of both rules; and it read into a parenthesised group rather than over it, so the space asked for in a { b (x:y): red; } was written inside the group. Every one of them is answered like any other declaration now, which cuts both ways: a declaration whose real colon already has the space these rules were writing elsewhere is no longer reported at all. Where the text in front of the colon ends in an inline comment the fix still declines to write, a space put there being commented out (see #88).
    • function-parentheses-newline-inside reads the runs beside a function's parentheses the way PostCSS's tokenizer reads whitespace now (see #496), so a line break standing behind a vertical tab no longer satisfies an always option — such a character is a word, the run beside the parenthesis holds no break, and the break the option asks for is written and reported.
    • The color-hex-case, function-comma-*, number-* and unit-case rules now read a call whose name a hexadecimal escape welds to the word in front of it (see #344). CSS closes such an escape with one whitespace character belonging to the escape rather than to the text, so a { b: \61 url(13PX); } names one call, aurl, which lightningcss compiles to a { b: aurl(13px); }, lowercasing that unit itself, and Sass to a { b: aurl(13PX); } — an ordinary call to both, whose arguments are the author's. postcss-value-parser reads no escape and hands that call back named url alone, which is what these rules matched against, so everything such a call held was passed over as an address's. The name is gathered back together now, and what stands inside is read like any other value. The other half of this reading, where an address written with an escape stops being rewritten, is under Fixed below.
    • The selector-descendant-combinator-no-non-space rule now reads a selector whose comment the parser carries across a parenthesised group (see #159). A group standing where a combinator belongs is nothing postcss-selector-parser has a place for: it reads the group as a combinator whose value is the whitespace in front of it and the group itself, and files a comment standing between the two behind that node rather than inside it, so .foo /*c*/\t( )\t.bar came back out of the parser as .foo ( )/*c*/\t\t.bar — the comment across the group, and a tab where none was written. The rule passed such a selector over, and a list at a time, so a run standing in a neighbouring selector went unreported with it. The node is given its own text back now, so the group is reported where it stands and the whitespace behind it is collapsed like any other descendant combinator's, the comment keeping the place the file gives it. Only a comment with a space in front of it was ever read that way, however wide the whitespace is: that space is what the value of such a combinator opens with, while a comment standing behind a tab or a line break the parser already prints as the file spells it.
    • The selector-descendant-combinator-no-non-space rule now reads a selector carrying an inline comment under postcss-scss (see #158). That syntax rewrites such a comment into a block comment in the copy the rule reads, keeps the source spelling in the copy it prints, and the two drift apart by two characters per comment, so the rule used to pass the whole selector list over. Every position is now translated back into the file's own coordinates, and a fix is written to both copies with the comments spelled the way the file spells them. The whitespace standing behind an inline comment is passed over on its own: the line break in it is what closes the comment, so a single space could not be written there, and asking for one would leave a warning no run of --fix could clear.
    • The selector-pseudo-class-parentheses-space-inside rule now reads a selector carrying an inline comment under postcss-scss (see #163). It used to pass such a selector over, as #161 left it: the two copies that syntax keeps of a selector drift apart by two characters per comment, so a position counted in the copy the rule reads points past the character it is about, and a fix written there never reaches the file. Both are answered now, so the pseudo-classes of such a selector are spaced out like any other. Where the whitespace in front of the closing parenthesis is the line break that closes an inline comment, that end is passed over instead: a space written there would take the parenthesis into the comment, and taking the break away would do the same.
    • The selector-pseudo-class-parentheses-space-inside rule now reports the whitespace standing in front of a closing parenthesis where a comment closes the arguments (see #128). The parser kept none of it, so the never options passed a:not( /**/ ) over while reporting the same space in a:not( b /**/ ); both are now read alike.
    • The declaration-colon-space-after rule now looks for the whitespace after the colon where a custom property whose value holds a comment actually keeps it (see #109) (@VChet):
      • the always options no longer report --a: /*comment*/ !important;, whose single space is already in place, and no longer pass over --a:/*comment*/ !important;, which has none at all;
      • their fix no longer adds a space of its own on every run, so two spaces or a tab after the colon now become the single space asked for;
      • the never option now takes the whitespace away instead of reporting a fix and leaving the declaration as it was, and no longer reports one that has no whitespace to begin with;
      • a space or a tab standing in front of the colon is no longer counted as one standing after it.
    • The declaration-colon-*-after rules now look for the whitespace behind the colon where a declaration whose value holds no word of its own actually keeps it (see #371). PostCSS hands that whitespace to raws.between only where the value has a word to leave behind; where all that stands behind the colon is whitespace, comments and a flag, raws.between ends at the colon and the run stays at the head of the value instead — in the raw of it where PostCSS keeps one, and in the value itself where it does not. Only the guard #109 above left behind ever looked there, and only for a custom property. The declaration is read now down to the end of its value, as the file prints it, and the run is moved to where PostCSS itself keeps it whenever a value has a word before anything is written over it, so a { color: !important; } and a { color: /*comment*/\t!important; } are answered like any other declaration:
      • the always and always-single-line options of declaration-colon-space-after no longer report a declaration whose single space is already in place, and their fix no longer writes a space of its own beside the run rather than over it, which used to grow the declaration by a space on every run;
      • the text those options count the lines of is that declaration's own value now, where it used to be the text around it: the value of a { color\n: !important; } is empty, and an empty text stands on one line, so always-single-line speaks about that declaration as it always has about a { color\n: pink; }, and always-multi-line of declaration-colon-newline-after is silent about it as it always has been about the twin;
      • its never option now reports such a run and takes it away, instead of passing the declaration over in silence;
      • declaration-colon-newline-after no longer reports a declaration whose break already stands where the option asks for it, and no longer writes a line break of its own on every run under either of its options;
      • the break that rule writes now goes behind a comment standing on the colon's own line rather than in front of it, as it always has where the value has a word, so the position such a problem is reported at moves to the end of that comment.
    • The declaration-colon-space-before and declaration-colon-space-after rules now work on the declaration's own colon instead of the first colon they come across (see #92). A comment standing in front of the colon may hold a colon of its own, an URL for one, and used to be taken for the declaration's:
      • the fix no longer edits the text of such a comment;
      • the never options no longer miss the real violation hiding behind it;
      • the always options no longer report a declaration that is already correct.
    • The declaration-block-semicolon-newline-after, declaration-block-semicolon-newline-before, declaration-block-semicolon-space-after and declaration-block-semicolon-space-before rules now check the declarations of an inline style attribute (see #49). A page gives such an attribute a root of its own with no rule inside it, and the four rules used to pass over every declaration whose parent is not a rule, so nothing was reported for style="color: pink;top: 0;" in an HTML, Vue, Svelte or Astro file, while the <style> block of the same page was checked as usual. The top level of a Sass file is left alone as before, since a variable written there is not a declaration block.
    • The selector-descendant-combinator-no-non-space rule now reports a parenthesised group standing after a space where a combinator belongs, .foo ( ) .bar for one (see #125). The rule used to read a combinator only where its value was a single space, so every such selector went past unseen; a group holding one space or none, .foo ( ) .bar and .foo () .bar, is reported alongside the rest. Nothing can be written to repair such a selector, so the problem is reported and the code left exactly as it was.
    • The selector-descendant-combinator-no-non-space rule no longer turns itself off for a selector carrying a comment (see #124). One comment anywhere in a selector list used to silence the rule for the whole list, so a violation standing in a neighbouring selector went unreported along with it:
      • a descendant combinator holding comments is now measured run by run, each stretch of whitespace reported at its own position and collapsed on its own, so that every comment stays where the author put it;
      • the whitespace after a comment that follows a combinator of another kind, .foo > /*comment*/ .bar for one, is passed over, since there is no descendant combinator there to measure;
      • an illegal combinator carrying a comment, .foo /*comment*/ ( ) .bar for one, is reported as #125 has it, and left exactly as it was.
      • a selector carrying an inline comment is read as well, which was #158 and is answered below.
      • a selector the parser does not give back as it took it is passed over too, which is #159: a comment standing in front of a parenthesised group is filed behind it, and nothing the rule could say about such a selector would match the file.
    • The indentation rule now measures the lines a comment used to hide from it (see #194). A selector line holding nothing but a block comment was blank in the copy the rule read and passed over in silence, and is brought to its level now, in a plain CSS file as under postcss-scss. A pair of literal slashes in a plain CSS selector — text to CSS, which has no comment of that kind — used to swallow the line break behind it whole, so the lines after it went unmeasured too, and are measured now. And a line that was already at its level behind a comment is no longer reported at a drifted position, so a false warning goes with the false silences.
    • The indentation rule now measures the lines standing behind an inline comment in a declaration's value or in an at-rule's parameters (see #236). The search that finds the line breaks of such a text read the break closing an inline comment as part of that comment and never handed its position over, so every line after it went unmeasured: the second line of a { b: 1px // c drew nothing at all, where the same file spelled with a block comment of exactly that width was reported and brought to its level. That search is handed a copy with the comments blanked out of it now, the one the rules reading a value for a comma or a bang are already handed, so a value, the arguments of a function inside it and an at-rule's parameters are all measured whichever way their comments are spelled, under postcss-scss and postcss-less alike. A line of a selector holding nothing but an inline comment is measured too, which it had not been since #194 left such a line blank in the copy the scan reads: every line is measured in the text the file spells instead, so a, followed by a line carrying only // c is brought to the level of the list like any other. In a value and in a set of parameters such a line was measured all along, and still is. And a double slash the file spells no comment with no longer hides the lines behind it, in a selector and in a set of parameters as in a value: a { b: url(http://x/y.png) followed by a mis-indented line is reported like any other, @import url(http://x/y.css) followed by one is too, and a plain CSS selector carrying such a pair no longer has the line break behind it swallowed along with the pair. The scan is told which syntax spelled the text now, so a double slash is read as a comment only where one is spelled that way — and the */ closing one block comment beside the /* opening the next is no longer read as a pair at all, so a { b: 1px/*x*//*y*/ followed by a mis-indented line is reported as well.
    • The indentation rule now reports every mis-indented line of an at-rule's parameters holding comments, at the line and column the file spells (see #65). The lines were sought in a copy of the parameters with the comments taken out: a line holding nothing but a comment was blank there and passed over in silence, and the warning that did appear was placed by an offset into that shorter text, at 1:30 where the file has 2:3. The scan reads the copy the file spells now and the fix writes to it, so both mis-indented lines of the issue's @use './button' with ( … ) are reported, each asking for the 1 tab it needs, and every comment survives the fix that used to strip all three.
    • The value-list-comma-*, media-query-list-comma-* and function-comma-* rules now report a comma standing behind an address (see #153). The search that finds the commas of a value and of a media query list read the double slash of url(http://x/y.png) as the opening of an inline comment, so everything from there to the end of the line was comment text to it. In a value that took the closing parenthesis of the address with it, and the count of open parentheses never came back down, so every comma that followed — on the address's line and on every line after it — stood inside a function's arguments as far as the search was concerned, where it passes them over; a media query list is read without skipping a function's arguments, so there it was the commas on the address's own line that were lost. The four function-comma-* rules read the same double slash the same way, through a pattern of their own, and said nothing about the comma of image-set(url(//cdn/a.png) 1x ,url(//cdn/b.png) 2x). All twelve are told which double slash opens a comment and which only looks like one now, so a { b: url(http://x/y.png),'z'; } is reported like any other value list, and fixed by the ten of them that fix anything. Nothing about this needs a comment anywhere, or any syntax but plain CSS: an address on its own was enough.
    • The declaration-bang-space-*, media-feature-colon-space-* and media-feature-range-operator-space-* rules now read what stands behind an address (see #215). The search these rules place their matches with reads a double slash as the opening of an inline comment wherever it stands, the one in url(http://x) among them, and everything from there to the end of the line was comment text to it, so a { b: url(http://x)!important; } drew nothing from either bang rule and the second feature of @media (min-width: url(http://x)) and (max-width:1px) drew nothing from any of the other four. They are told which double slash opens a comment and which only looks like one now, as #153 told the comma rules; nothing about this needs a comment anywhere, or any syntax but plain CSS.
    • The value-list-comma-*, media-query-list-comma-*, function-comma-*, declaration-bang-space-*, media-feature-colon-space-* and media-feature-range-operator-space-* rules now read three double slashes the file does not spell a comment with (see #216). The search these rules place their matches with was handed a copy in which every double slash that opens no comment is written over, and three of them could not be: the */ closing one block comment and the /* opening the next spell a pair between them, and neither slash can be written over without taking a comment away, so 1px/*x*//*y*/,2px drew nothing; a pair whose second slash opens a block comment was held back for the same reason, though the one in url(a//*b*/) opens nothing, so url(a//*b*/),2px drew nothing either; and a pair standing in plain CSS, which spells no comment that way at all, was read as one, so myurl(//a),2px, image-url(//a),2px and a//b,2px drew nothing either.     • The fixes of the whitespace rules outside the shared-run machinery of the declaration's colon and semicolon — declaration-bang-space-before and -after, declaration-colon-space-before, the value-list-comma-*, selector-list-comma-*, media-feature-* and media-query-list-comma-* families, and function-parentheses-newline-inside — now read the run they rewrite the way PostCSS's tokenizer reads whitespace: a space, a tab, a line feed, a carriage return or a form feed, and nothing else (see #496). A vertical tab and a no-break space are words to the tokenizer, and these fixes used to read them with \s and carry them off with the run in silence: declaration-bang-space-before: never turned a { b: c\v !important; } into a { b: c!important; }. Such a character is part of the word beside the run now: the fix rewrites the run alone and the character stays — and where nothing but such characters touches a parenthesis, function-parentheses-newline-inside's never-multi-line no longer reports a run that is not there.
    • The declaration-colon-newline-after rule no longer writes its line break into the text of a comment opened as /*/ (see #400). The rule lets a comment stand on the colon's own line and asks for the break behind that comment; it found the end of that comment by searching for */ from the colon, and a comment opening on a solidus lends that solidus and the star in front of it to the search, three characters into a comment that has not closed yet. The search starts behind the comment's own opening now, so a { b: /*/ x */y; } gets its break behind the whole of the comment and the warning stands where the comment ends rather than inside it. /*/ */, /*/x*/, /*/*a*/, /*/*/ and /*//*/ all closed early the same way.

A file of plain CSS is untouched, and so is always under every syntax; a syntax that answers nothing about itself is read as a preprocessor here, which leaves whitespace standing rather than a file broken.

    • The declaration-colon-space-after and declaration-colon-newline-after rules, and the declaration-block-semicolon-space-before and declaration-block-semicolon-newline-before rules, now settle between them who writes the whitespace of a declaration whose value is nothing but that whitespace (see #416). In a { color: ; } the run behind the colon is the run in front of the semicolon, and one character cannot answer to two options; the colon rules write into one place and the semicolon rules read another, so a pair such as declaration-colon-space-after: always beside declaration-block-semicolon-space-before: never used to take the run in turns — a { color:; } on one run of --fix, a { color: ; } on the next, and so on for ever, each run writing a diff and each leaving one warning. Each of the four rules now reads the settings of the other three out of the configuration, wherever it lists them, and writes the run only where every rule listed behind it that speaks of the declaration is content with a spelling of the run it is content with too, or would silence it with what it writes; otherwise it reports the run without a fix, so the file rests on what the rules behind it write and the warning of the rule the configuration contradicted stands where it was hidden before. A pair asking for the same thing — a single space from either end, a line break from either end — writes as it always did, and so does every declaration whose value has a word of its own. The two colon rules listed against each other are asked about one and the same run from the same end, and what is left of that pair — a value carrying a flag, a comment holding a colon — is #484 and #388 rather than this change's.

  • One run of --fix now does the work that run's own writing uncovers, instead of leaving it for the next one:

    • The function-parentheses-newline-inside rule now reads a value against the inline comments it holds once the fixes collected so far are written into it (see #288). The spans such comments occupy were found once per declaration, before the value was walked, and a call opening inside one of them is passed over — its parentheses are the text of a comment rather than parentheses of the value. The always and always-multi-line options write line breaks, though, and a line break is what closes a comment opened by a double slash. So in a { t: foo(1px // c) calc(/*b*/, a line break, ,2px, a line break, ); }, where the comment runs from the double slash past calc( to the first break of the value, the break the fix writes in front of the closing parenthesis of foo closes that comment early and leaves calc( standing in code with its own break still missing. The rule went on reading the value against spans it no longer had, said nothing about calc(, and handed back a file one break short of what the option asks for; a second run of --fix wrote that break and a third settled, so nothing ran away. The spans are found again now, wherever a fix has been written and before the next call is read, and the one run writes both breaks. A run without --fix is unchanged, and writes nothing: as the file stands, calc( is the text of a comment.
    • The named-grid-areas-alignment rule now asks whether a declaration spans lines of the text its fix will leave rather than of the text it was handed (see #402). That answer decides whether the cells of a row are padded out to the width of the column they stand in, and it used to count every line break of the value, a break standing inside a row among them — while every fix this rule makes to a row collapses the whitespace inside it, breaks included. So a value whose only break stood inside a row had its cells padded by the very run that was taking that break out of it: a { grid-template-areas: "a, a break and two tabs, a" "bb bb"; } came back from --fix as a { grid-template-areas: "a a" "bb bb"; }, and the next run, reading a declaration that no longer spans lines, took the padding away again and left "a a" "bb bb". A neighbouring row was written twice over the same way — "aaa, a break, aaa" "b b" came back with its second row widened to "b b" before the next run narrowed it again — and under alignQuotes a row holding nothing but a break came back as five spaces between its quotation marks before the next run emptied it. Plain CSS reaches this, with no comment and no custom syntax needed. A break standing inside a row is a character the fix is about to write over now, and only a break standing outside every row makes a declaration one that spans lines — everything of a value that is no row is handed back character for character, wherever it stands and whatever it is: the whitespace in front of the first row, between two of them or behind the last, a comment, a call, a word carrying an escaped break. So the first run writes what the second used to, and what a warning says of a value is true of the file the run that raised it leaves behind.

  • A walk over a run of comments now costs a step per comment rather than a stack frame:

    • The at-rule-semicolon-newline-after, declaration-block-semicolon-newline-after and declaration-block-trailing-semicolon rules now read a stylesheet holding a long run of comments (see #360) (@chiliec). All three step over such a run through one walk — from a node's own sibling in the first two, from the front of a block in the third — and that walk called itself once per comment, so a long enough run ended the whole run in RangeError: Maximum call stack size exceeded and no file was reported on at all; around eleven thousand comments is the threshold on Node 26, and twenty thousand throws every time. A comment costs that walk a step now rather than a stack frame, so a stylesheet is read whatever run of comments it holds. Every answer the walk gives is the answer it gave before, so nothing else about the three rules moves. The same walk had been copied into block-opening-brace-newline-after, which had a write of its own to make and reached this one through no caller; that copy is folded back into this walk below.
    • The block-opening-brace-newline-after rule now reads a stylesheet holding a long run of comments at the head of a block (see #409). It kept a copy of that walk rather than calling it, because it has a write of its own to make on every comment it steps over: the line break standing in front of a comment is carried onto the node behind it, so that a comment at the head of a block may hold the break the option asks for. The copy went on calling itself once per comment after the walk it was copied from stopped doing so, and it fell sooner than that walk did — eight thousand comments throws every time on Node 26, where the walk above took around eleven thousand. The copy is gone: the walk above takes that write as a callback of its own, so one walk steps over a run of comments for every rule that asks, and the next fix to it reaches all four at once. Every answer the rule gives is the answer it gave before, measured over 75 456 runs on either side of the change — runs of up to three comments, block and inline, under up to seven spellings of the whitespace standing around them, in a rule and in a nested at-rule, in a block ending in a declaration, in a comment and in nothing at all, under all three options, three syntaxes and both settings of --fix — byte-identical throughout. A block holding nothing but comments still comes out of --fix rewritten and reported on not at all, which is older than this change and filed as #410.

  • --fix no longer writes into a file the rule reports nothing about:

    • The block-opening-brace-newline-after rule no longer breaks the lines of a block holding nothing but comments (see #410). The rule carries the line break standing in front of a comment onto the node behind it, so that a comment at the head of a block may hold the break the option asks for, and puts that whitespace back once the check is done; a block whose comments stand in front of no node at all ended the check before the whitespace was put back, so a {, a break and /*1*/ /*2*/ /*3*/} came back from --fix with every comment on a line of its own and no warning to explain the rewrite. Such a block comes out of --fix as it went in now, under every option.
